# 18-flip, refactored

The single-file FLIP fluid demo (`ref/18-flip.html`, Ten Minute Physics episode 18
by Matthias Müller) split into modules - with the simulation and the rendered
output verified identical to the original, not assumed identical.

The page also carries two small panels: settings, where the particle count can be
changed and applied, and debug, which reports frame rate, timings, particle
counts and grid statistics while it is switched on. See
[WORKFLOW.md](WORKFLOW.md) for how versions and releases work - committing is
local, and pushing is the step you take when you are satisfied with a piece of
work.

`ref/18-flip.html` is a byte-identical copy of the original single file
(sha256 `30682CCD...`), kept so the project stands on its own. Nothing in it has
been modified. Every claim below is checked against it by a script in `test/`.

## Run it

Double-click **`index.html`**. That is the whole thing: one self-contained file,
no server, nothing to install. It is generated by `tools/bundle.mjs` from
`dev.html` plus `src/`, so it is never the place to edit - but it is the place to
open, and the file a static host serves by default.

To work on the source instead:

```
node tools/serve.mjs          # default port 8080
node tools/serve.mjs 9000     # or pick one
```

Then open `http://localhost:8080/dev.html`, or double-click `start.cmd`, which
starts the server and opens that page for you.

Only `dev.html` needs the server, because it loads the modules in `src/` and
browsers refuse to fetch module scripts from `file://` pages: Chrome 153 rejects
them with *"Failed to fetch dynamically imported module"*. That was measured,
not assumed - see `test/probe-module.html`. Open `dev.html` from disk and it now
says so rather than showing a blank canvas.

After editing a module, run `node tools/bundle.mjs` to refresh `index.html`.

## Behaviour preserved on purpose

The solver is a line-by-line port. Same math, same `Float32Array` layouts, same
iteration order, same constants, so a given state produces byte-identical
output. Specifically kept:

- the dam-break initial condition, and every default (resolution 100, 50
  pressure iterations, `dt = 1/60`, `flipRatio = 0.9`, `gravity = -9.81`,
  obstacle radius 0.15)
- one `simulate()` per animation frame, single substep - no fixed-timestep
  accumulator was introduced, which would change the motion
- the canvas is measured once at load; there is still no resize handling
- the disc is drawn every frame regardless of `showObstacle`, which the draw
  path never reads
- `frameNr` increments even while paused, matching the original's unbraced `if`
- `event.x`/`event.y` became `event.clientX`/`event.clientY`, which are the
  standardised aliases of the same values

## Latent problems fixed

Each of these is behaviour-neutral, and the parity run proves it:

- `updateParticleDensity()` read a global `f` while its siblings used `this`.
  It now reads `this.particleDensity`. Same array today, silently empty after
  any rename.
- the solver reached into the global `scene` for the obstacle velocity. That is
  now a parameter, so `FlipFluid` has no outside dependencies.
- `setObstacle()` assigned undeclared `dx`/`dy`, which are implicit globals in
  a classic script and a `ReferenceError` under module strict mode.
- the call into the solver passed `scene.colorFieldNr`, a leftover from another
  episode that is not a parameter and is always `undefined`.
- removed: `U_FIELD`/`V_FIELD`, `cnt`, `toggleStart()` (which targeted a
  `#startButton` that does not exist), the unused `.button` rule, the unused
  `or`/`or2` locals, one dead read loop, and the commented-out experiment
  blocks.
- markup: the viewport meta tag was outside `<head>`, and there was no charset
  or `lang`. Inline `onclick`/`onchange` attributes are gone, wired in
  `src/app/UI.js` instead.

## Verification

Nothing here needs a dependency installed.

```
node tools/verify.mjs            # before committing: rebuild index.html + behaviour check  (~3 s)
node tools/verify.mjs --full     # adds both original-parity harnesses                   (~1.5 min)
node test/baseline.mjs           # behaviour vs test/baseline.json
node test/baseline.mjs --update  # re-record it, after a change you meant to make
node test/parity.mjs             # headless parity against the original demo
node test/parity-browser.mjs     # rendered-output parity in headless Chrome
```

`test/baseline.mjs` is the day-to-day regression net. It compares the simulation
against `test/baseline.json` - behaviour you record, and re-record deliberately
when a change is intended - so a failure means "behaviour moved and you did not
say so". That is the check to run while adding features.

The two parity harnesses below are the provenance check instead: they compare
against `ref/18-flip.html`, so they pass only while behaviour is unchanged.
Deliberately changing the physics will fail them, which is expected. Both roles
are explained in `WORKFLOW.md`.

**`test/parity.mjs`** boots the original from `ref/` inside a VM with a DOM and
WebGL stub, runs the refactored build through the same script, and compares the
raw bytes of every simulation array. There is no randomness and no wall-clock
input, so a fixed sequence is fully deterministic. The run is 60 dam-break
frames, then a 30 frame drag of the disc, then 30 settle frames.

```
RESULT: PASS - all 13 checks match, every simulation array is byte-identical
```

46 fields compared per snapshot: 17 typed arrays (`particlePos`, `particleVel`,
`particleColor`, `particleDensity`, `u`, `v`, `du`, `dv`, `prevU`, `prevV`, `p`,
`s`, `cellType`, `cellColor`, and three scratch arrays), 11 solver scalars, and
18 scene scalars - before and after the run. It also checks that the generated
`index.html` is genuinely self-contained: no module tag, no external script or
stylesheet, with the modules and `app.css` inlined.

**`test/parity-browser.mjs`** loads all three builds in the same headless Chrome -
the original over `file://`, `dev.html` over http, and the generated `index.html`
over `file://` - drives them through an identical sequence, and compares what
actually came out. Both are checked against the original on every axis.

```
RESULT: PASS - all 19 checks match
```

What it establishes, per build:

| Check | Result |
| --- | --- |
| on-load frame | identical canvas, identical state digest |
| simulation advanced | digest changes, 32,856 particles, so the comparison is not two blank frames |
| simulation state | identical digest in-browser |
| canvas pixels | byte-identical PNG, sha256 `f9875e33...` |
| controls take effect | Grid checkbox and slider drive all three identically: `showGrid=true`, `flipRatio=0.5` |
| canvas after controls | identical, and different from the pre-control frame, so the grid pass really rendered |
| page chrome | 14 geometry/style fields identical, down to computed border and font |
| page screenshot | byte-identical, 331,564 bytes |
| console | no errors or uncaught exceptions in any build |

The page screenshot matching matters here beyond the canvas: the generated
`index.html` carries an inlined copy of `app.css` instead of the linked
stylesheet, so a byte-identical screenshot also proves the inlining did not
disturb layout.

Screenshots land in `test/artifacts/`.

One note for anyone re-running the browser harness: headless Chrome needs
`--no-sandbox --disable-gpu-sandbox` here, otherwise its GPU process crashes on
repeat and the run hangs. WebGL then renders through SwiftShader. Both builds
are measured in that same environment, so the comparison holds.

## Still open

- HiDPI and resize handling. The canvas is still measured once, so on a scaled
  display it renders at logical resolution. Adding it changes the backing store
  size, and therefore changes output, which is exactly what this pass was meant
  not to do.
