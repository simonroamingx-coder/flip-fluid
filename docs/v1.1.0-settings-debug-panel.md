## 1. Document Purpose

This document specifies the implementation of a **Settings Panel** and **Debug
Panel** for the 2D Web FLIP Fluid Simulator.

The current project already has a modular architecture:

```text
flip-fluid/
├── index.html
├── dev.html
├── src/
│   ├── main.js
│   ├── app/
│   │   ├── Input.js
│   │   ├── UI.js
│   │   ├── canvas.js
│   │   └── loop.js
│   ├── core/
│   │   ├── FlipFluid.js
│   │   ├── constants.js
│   │   ├── obstacle.js
│   │   ├── scenarios.js
│   │   └── scene.js
│   ├── render/
│   │   ├── Renderer.js
│   │   ├── glUtils.js
│   │   └── shaders.js
│   ├── styles/
│   │   └── app.css
│   └── utils/
│       └── math.js
```

The new system should preserve this separation.

The main goals are:

1. Allow users to change the particle count.
2. Allow users to enable/disable debugging.
3. Display runtime simulation information.
4. Display performance information.
5. Provide a foundation for future debugging visualization.
6. Avoid adding unnecessary overhead to the normal simulation.
7. Keep simulation code independent from UI code.

The tree above is as supplied; see appendix A for what the repository actually
contains today.

## 2. Design Principles

### 2.1 UI must not control the solver directly

The UI should not contain FLIP algorithm logic.

Bad:

```text
UI → directly modify FlipFluid arrays
```

Preferred:

```text
UI
 ↓
Configuration
 ↓
Scene
 ↓
FlipFluid
```

The solver should receive configuration/state rather than knowing where that
configuration came from.

### 2.2 Debugging must be optional

Normal execution should have minimal debug overhead.

Conceptually:

```js
if (debug.enabled) {
    collectDebugData();
}
```

The simulation should still work when debugging is disabled.

### 2.3 Particle count changes require simulation reinitialization

Changing particle count affects arrays such as:

```text
particle positions
particle velocities
particle previous velocities
particle densities
particle IDs / temporary buffers
```

Therefore, the first implementation should **not dynamically resize the particle
arrays while the simulation is running**.

Instead:

```text
Change particle count
        ↓
Press Apply
        ↓
Reinitialize scene
        ↓
Create new particle arrays
        ↓
Restart simulation
```

This is simpler and safer.

## 4. Settings System

Create a centralized simulation configuration.

Recommended conceptual structure:

```js
const config = {
    particleCount: 10000,

    debug: {
        enabled: false,
        showParticles: false,
        showGrid: false,
        showVelocity: false,
        showPressure: false,
        showCollision: false
    }
};
```

The exact location/name can be adjusted to fit the existing architecture.

The important point is that configuration should have **one authoritative
source**.

## 5. Particle Count

### 5.1 UI

The Settings panel should provide:

```text
Particle Count

[ slider ]

10,000

[ Apply / Restart ]
```

Recommended initial range:

```text
Minimum: 1,000
Maximum: 50,000
Step:    1,000
Default: existing project particle count
```

The exact maximum should be adjustable later because performance depends heavily
on hardware.

### 5.2 Slider behavior

Dragging the slider should only modify the **pending configuration**.

It should NOT recreate the simulation on every slider movement.

Bad:

```text
Slider movement
    ↓
Create 10,000 particles
    ↓
Create 11,000 particles
    ↓
Create 12,000 particles
    ↓
...
```

Preferred:

```text
Slider movement
    ↓
Change displayed value

User presses Apply
    ↓
Reinitialize simulation
```

## 6. Scene Reinitialization

Changing particle count should cause the simulation to restart.

The intended flow is:

```text
UI
 │
 │ Apply particle count
 ▼
Configuration updated
 │
 ▼
Scene reset/recreated
 │
 ├── create FLIP solver
 ├── create particle arrays
 ├── initialize particle positions
 ├── initialize velocities
 └── initialize grid
 │
 ▼
Simulation continues
```

The existing scene creation and scenario setup should be reused rather than
duplicated.

The implementation should avoid creating a second independent initialization
path.

## 11. FPS Measurement

FPS should be calculated from frame timing.

Basic principle:

```js
const now = performance.now();
const frameTime = now - previousTime;
const fps = 1000 / frameTime;
```

The displayed value should preferably be smoothed.

Do not display a wildly fluctuating value such as:

```text
60
59
42
60
38
61
```

Instead use an averaging window or exponential smoothing.

For example:

```text
FPS: 59.7
```

---

## 12. Frame Time

Display:

```text
Frame Time: 16.7 ms
```

This is useful because FPS alone hides important information.

Relationship:

```text
FPS ≈ 1000 / frameTime
```

Examples:

```text
60 FPS  → 16.67 ms
30 FPS  → 33.33 ms
20 FPS  → 50.00 ms
```

## 13. Simulation Profiling

The simulation loop should be divided into measurable stages.

The initial profiling structure should be approximately:

```text
Frame
│
├── Simulation
│   ├── Particle update
│   ├── Particle → Grid
│   ├── Pressure solve
│   ├── Grid → Particle
│   └── Collision / integration
│
└── Rendering
```

Use:

```js
const start = performance.now();

// operation

const elapsed = performance.now() - start;
```

For example:

```js
const start = performance.now();

simulateOnce(scene);

runtimeStats.simulationTime =
    performance.now() - start;
```

Do not add profiling calls to every low-level loop iteration.

Profiling should happen around meaningful stages.

## 21. Velocity Visualization

Velocity vectors can provide extremely useful FLIP debugging information.

**What was built.** Vectors are written for every fifth cell, from the centre of
each fluid cell along the mean of the faces bounding it - in this solver `u` lives
on a cell's left face and `v` on its bottom one, so a cell's own velocity is the
mean of two faces in each direction. They draw over whichever colour field is
showing rather than replacing it, since that combination is the useful one. The
sampling interval and the display scale are the two knobs this section mentions;
they are constants in `src/debug/fields.js`, which is what "eventually" allows for.

The length is the cell's speed times a scale, capped. The cap is the part worth
recording. Measured on the dam-break scene, the median speed is 0.63 to 1.70 while
the fastest cells reach 4.3 to 8.2 - the maximum is five to seven times the median
- so no single linear scale serves both ends. At a scale that made the fastest
arrows sane the typical flow was 2 to 6 per cent of the tank width and hard to
read; at a scale that made the typical flow readable, individual cells drew lines
across 16 to 30 per cent of it. With the cap, the middle of the distribution still
reads linearly and everything above it draws the same length, so the view answers
"which way is the fluid going" everywhere and "how fast" up to the cap.

For each selected grid cell or particle:

```text
position
   │
   └──────► velocity
```

Example:

```text
●────►
```

Avoid drawing every velocity vector at very high resolution.

Eventually provide a debug sampling interval:

```text
Velocity display scale
Velocity sampling
```

## 22. Pressure Visualization

Pressure can be displayed as a scalar field.

Conceptually:

```text
Low pressure ───────── High pressure
```

The exact rendering representation can be added after runtime statistics are
working.

The important requirement is:

**Debug visualization must read the actual pressure data generated by the
solver.**

It must not calculate a separate approximation.

**What was built.** Red intensity, scaled to the largest magnitude present and
smoothed over time so the whole field does not jump when a peak moves. The first
version drew the sign instead - red for pushing, blue for pulling - and it was
the wrong emphasis: `p` is signed, but the negative side is not physical here
(no free-surface pressure boundary condition, no cavitation model), so a second
colour lent the suction more meaning than it has. A single magnitude channel
answers the question the view is for: where is the solver working hardest. In a
dam break that is the fluid packed against the floor, with the field fading
towards the free surface.

## 23. Performance Requirements

The debug system must not significantly slow down normal simulation.

When:

```text
Debug = OFF
```

the application should execute essentially the existing simulation path.

Avoid:

```js
console.log(...)
```

inside particle loops.

Never do:

```js
for (let i = 0; i < numParticles; i++) {
    console.log(...);
}
```

This will destroy performance.

---

## 24. Runtime Data Update Frequency

The UI does not need to update every simulation operation.

Recommended:

```text
Simulation:
    every frame

Statistics:
    every frame

DOM:
    approximately 5–10 times per second
```

For example:

```text
Simulation: 60 FPS
Debug UI:   10 FPS
```

This prevents excessive DOM updates.

The simulation and UI update frequencies should therefore be independent.

**What was built, and what this rule does not cover.** The panel's numbers are
refreshed about seven times a second. The debug *views* are not: they are
recomputed and redrawn every frame. The first version applied this section's rate
to the picture as well, and a field that steps seven times a second reads as
stutter no matter how little it costs - which is what the rule is about, DOM
writes, rather than about rendering.

The picture also has to be cheap enough to redraw every frame, which is why the
views are one textured quad over the grid rather than one sprite per cell: an
upload of three bytes per cell and a single draw call, against tens of thousands
of fat points. `test/parity-browser.mjs` measures the refresh rate against the
frame rate, so "every frame" is checked rather than assumed.

## 34. Error Handling

Invalid particle counts should be clamped.

For example:

```js
particleCount = Math.max(
    MIN_PARTICLES,
    Math.min(MAX_PARTICLES, particleCount)
);
```

The UI should also prevent invalid input.

If initialization fails because the requested particle count is too large, the
application should retain the previous working configuration where practical.

## 35. Reset Behavior

When applying a new particle count:

```text
Old simulation
      ↓
Stop/update loop safely
      ↓
Create new scene state
      ↓
Initialize particles
      ↓
Initialize grid
      ↓
Reset runtime statistics
      ↓
Resume simulation
```

Runtime statistics should not retain misleading values from the previous
simulation.

For example:

```text
Before reset:
Simulation time: 184.3 s

After reset:
Simulation time: 0 s
```

The key architectural rule is:

> **The FLIP solver owns simulation data. The Debug system observes that data.
> The UI controls configuration and displays debug information. Neither UI nor

This keeps the project extensible as the simulator grows from a small
educational FLIP implementation into a more complete interactive
fluid-simulation tool.

# Appendix B - Decisions to make before starting

These are the places where the specification meets code that already exists.
They are worth settling first, because each one changes what the other stages
look like.

## B1. Particle count is currently derived, not chosen

This is the significant one. Today `src/core/scenarios.js` computes the particle
count from the tank rather than accepting it:

```text
res = 100                     → h = tankHeight / res
r   = 0.3 * h                  particle radius
dx  = 2r,  dy = sqrt(3)/2 * dx hexagonal spacing
numX, numY                     from the water block size and the tank size
maxParticles = numX * numY
```

So the count is an output of the scenario. Making it an input means choosing
which knob it turns, and each choice changes something else:

| Option | What it changes | Consequence |
| --- | --- | --- |
| Solve for grid resolution | keeps block shape and the `r/h` ratio | cell count and cost scale with it; the solver's grid changes size |
| Keep the grid, resize the water block | only the scenario | the simulation looks different; resolution is unaffected |
| Keep both, change particle radius | the particle-to-cell ratio | changes the character of the simulation, not just the cost |
| Treat it as a target, report the achieved count | nothing | hexagonal packing only produces certain counts; request ≠ reality |

The last row is worth taking seriously whichever route you pick: with a
hexagonal lattice you cannot hit an arbitrary number, so the panel should show
both the requested and the actual count, as the spec already does for
`Allocated` versus `Active` particles in section 15.

Also note that "Default: existing project particle count" is viewport dependent
today: the simulation domain comes from the canvas size, which comes from the
window. At a 1280×720 window the default is 25,900 particles; resize the window
and the same code produces a different number, which is currently the intended
behaviour. A slider default has to pick one of: the count at load, a fixed
number, or the count for a normalised domain.

## B2. `showParticles` and `showGrid` already exist

The current page has four checkboxes, and the first two are exactly these:

```text
[✓] Particles            scene.showParticles
[ ] Grid                 scene.showGrid
```

Section 4 puts them in `config.debug`. Keeping both would be the duplicated
authority section 2.1 warns about, so decide which survives:

* move them into the Debug panel (matches the spec; the top row shrinks), or
* leave them on the top row and have the Debug panel own only the new toggles.

Recommendation: move them, and keep the current defaults (`showParticles: true`,
`showGrid: false`) rather than the spec's `false`, so the page does not change
what it shows on load.

## B3. `config` versus `scene`

`src/core/scene.js` currently holds both kinds of thing in one object: settings
that a user could plausibly own (`gravity`, `dt`, `flipRatio`,
`numPressureIters`, `obstacleRadius`) and live state that is nobody's setting
(`frameNr`, `paused`, `fluid`, `obstacleVelX`).

A clean split, and the one the spec's data flow implies:

```text
config   what the user sets      particle count now; gravity, dt, iterations later
scene    live state, built from config by setupScene(scene, config)
```

Section 36 rules out the alternative of a global `particleCount`, and this split
is how you avoid needing one.

## B4. Where the panel lives, and the canvas

The canvas is sized from the window (`innerWidth - 20` by `innerHeight - 20`), and
the simulation domain follows from that size. A panel that takes layout space
does not change those numbers, but it can introduce a scrollbar, which changes
`innerWidth` and therefore the simulated domain.

Recommendation: an overlay panel, `position: fixed`, collapsible, with
`pointer-events: none` on any container that is not meant to be interactive.
The version stamp added in v1.0.0 works this way, and for the same reason: it
must not disturb the viewport.

## B5. Where the throttled UI update goes

Section 24 wants DOM updates at 5–10 Hz while the simulation runs at frame rate.
`src/app/loop.js` is the natural home: it already owns one `simulateOnce` plus one
`renderer.draw` per animation frame.

Two existing details to preserve while you are in there: there is exactly one
simulation step per frame with no accumulator, and `frameNr` increments even
while paused (it sits outside the `if (!scene.paused)` guard). Both are load
bearing for the behaviour baseline.

# Appendix C - Integration notes the specification does not cover

## C1. Reinitializing must reinitialize the renderer too

`Renderer.init(fluid)` builds a grid vertex buffer sized from `fluid.fNumX`,
`fNumY` and `h`, in the first version of the point shader. The particle buffers
are sized from `maxParticles`. After `setupScene` creates a new `FlipFluid`, the
renderer must be re-initialized as well, or it will keep sizes from the previous
grid. This is easy to miss because nothing throws: you get a visibly wrong or
partially drawn grid.

## C2. Per-stage profiling needs the solver's stages exposed

Section 29 asks for particle, particle→grid, pressure, grid→particle and
collision timings. `FlipFluid.simulate()` currently calls all of those
internally, in this order:

```text
integrateParticles → pushParticlesApart → handleParticleCollisions
→ transferVelocities(true) → updateParticleDensity → solveIncompressibility
→ transferVelocities(false) → updateParticleColors → updateCellColors
```

**How it was done.** `simulate()` takes an optional timing sink
(`simulate(..., timings)`) and measures its own stages, with the stage sequence
written once: a second copy of that sequence, in a caller that had to know the
order, would be free to drift out of step and report times for operations that no
longer happen in that order. With no sink the only cost is one boolean test per
stage, and the disabled path takes exactly the calls it took before.

Four checks cover it, in `test/profiling.mjs` and the browser harness:

```text
timing does not change the result   40 steps with a sink and without one leave
                                    46 state fields byte-identical
every stage is reported             all six buckets finite, non-negative, non-zero
stages fit inside the step          they are measured inside the total, so they
                                    cannot exceed it
stage timings appear while running  the live panel shows them, and they add up to
                                    the simulation time it reports
```

## C3. `performance.now()` is coarser than the numbers you want to show

Browsers clamp the clock — commonly to 100 µs, or ~5 µs with cross-origin
isolation enabled. Several of the stages above run in well under a millisecond at
low particle counts, so instantaneous per-stage values will be noisy and can read
as 0.0 ms.

Prefer a rolling mean over N frames, and say in the panel (or the docs) what the
measurement floor is, so a 0.0 ms reading is understood as "below resolution"
rather than "free".

## C4. The rendered-output parity harness pins the current page

`test/parity-browser.mjs` compares three things against the original page: the
canvas pixels, the simulation state, and the page chrome — 14 fields including
the body's child node list and the full-page screenshot.

That check is calibrated for v1.0.0. The version stamp in v1.0.0 was handled by
recording the badge and removing the element before comparing, which works for
one small addition. A settings and debug panel cannot be handled that way without
gutting the check.

Recommendation for v1.1.0: retire the DOM identity checks and keep the ones that
answer the question that still matters —

```text
keep:    canvas pixels, simulation state, on-load frame, grid pass, console clean
retire:  page chrome, full-page screenshot
```

Those two belong to the refactor, and they have already done their job. Retiring
them is a decision to record here, not a red test to discover later.

## C5. Several existing tests will need updating

If the panel moves the existing checkboxes, these break by design and need to
change with it:

* `test/parity.mjs` checks the checkbox ids in the markup, and that `UI.js`
  flips the same flags the original's inline handlers flipped (`TOGGLES` is
  exported from `src/app/UI.js` for exactly that check).
* `test/parity-browser.mjs` clicks the first unchecked checkbox to exercise the
  grid pass, and the probe counts `input` elements.
* `test/baseline.json` may move even if the solver is untouched, because the
  default particle count is part of the recorded scenario. Plan for
  `node tools/verify.mjs --update` and read the diff.

## C6. Reuse what the renderer already has

The grid pass already draws `fluid.cellColor`, which `updateCellColors()` fills
from particle density through `setSciColor()`. Pressure (`fluid.p`) and cell type
(`fluid.cellType`) are the same shape of data, so a first pass at "show pressure"
can reuse the existing point program with a different per-cell array and colour
mapping — no new shader required. Velocity vectors do need new geometry.
